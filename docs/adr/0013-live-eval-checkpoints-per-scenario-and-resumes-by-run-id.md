# Live-eval runs checkpoint per scenario and resume by run id

The Live eval is the one command that measures answer quality against the real provider, and it is the one most likely to die mid-run: ten cases, each a full workflow pass plus a judge call, over a network that can drop at any point. Before ADR-0013 an LLM failure on case nine threw away the measured work of cases one through eight. Every `backend.src.live_eval` command now checkpoints (2026-09-03): a run id — passed via `--run-id` or minted on the spot (UTC timestamp plus four random hex characters) — names one JSON file under `data/eval-runs/` holding the run's metadata plus each completed case's `EvalScenarioResult` (the exact shape the `--output` artifact gives a case), rewritten atomically (temp file + rename) the moment a case lands, through an `on_result` callback the shared `evaluate_scenarios` loop invokes per case; the harness itself never touches the filesystem. Re-invoking with the same run id runs only the pending cases and stitches checkpointed and fresh results into one report. The checkpoint is a per-scenario cache, never the source of truth: today's `LIVE_EVAL_SCENARIOS` list wins, so a case added to the list runs fresh and one removed leaves an unused record behind. A completed result substitutes only while its case's definition hash (SHA-256 over id, routing id, question, description, and the expected findings as the audit dump renders them) and the configured model still match; a hash mismatch, a model mismatch (results are model-sensitive, ADR-0009), or an unreadable file refuses the run — a quietly mixed measurement is worse than no measurement. An LLM failure exits 1 and a Ctrl-C exits 130, both printing the completed cases' numbers plus the exact resume command; `--output` is written on success only, and when it is, the artifact supersedes the checkpoint and the file is removed — without `--output` the checkpoint stays as the run's only record, and re-invoking the id re-serves the full report with zero LLM calls and zero precondition checks, because the work is done and recorded.

## Considered options

- **Checkpoint both runners** (`run_eval` Demo tripwires included) — rejected: the Demo suite is fast, judgeless, and CI-run; checkpointing it buys nothing and complicates the tripwire property (ADR-0001).
- **Resume by a separate `--resume ID` flag** — rejected: one flag with one meaning (an id with a checkpoint file is a resume) is one less state for the operator to hold; the abort message prints the exact command either way.
- **Tolerate stale checkpoints** (skip the mismatched case, re-run everything else) — rejected: results are model-sensitive and ground-truth-sensitive; silently mixing measurements from two definitions or two models dresses old numbers as new ones.
- **Fresh start on an unreadable checkpoint** — rejected: atomic writes make corruption unlikely, so when it happens something else is wrong; re-running ten paid cases is the wrong default, the operator decides.
- **Put the checkpoint loop inside `evaluate_scenarios`** — rejected: the harness is the shared pure scorer for Demo and Live; a per-case `on_result` callback gives the Live runner the hook without file I/O in the harness.

## Consequences

- `run_live_eval` grows `run_id` / `checkpoint_dir` optional parameters; `None` (every existing caller and test) behaves exactly as before checkpointing existed.
- A fully-checkpointed resume serves the report without `ensure_runnable` — a finished measurement can be re-printed from a machine that could no longer run a single case (no key, no store).
- `data/eval-runs/` is gitignored; checkpoint files are operator-local working state, not artifacts. Inside the stack `data/` is mounted read-only (the Corpus lives there), so the CLI checkpoints under `logs/eval-runs/` in that venue — resolved and named on the printed run-id line before the first request — and `--checkpoint-dir` overrides both.
- The harness's `evaluate_scenarios` gains an optional pure `on_result` callback; Demo scoring is unchanged (it passes nothing).
